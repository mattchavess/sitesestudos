01

Encapsulamento e modificadores de acesso

Encapsular significa esconder os detalhes internos de uma classe e controlar quem pode ler ou alterar seus atributos e métodos. Em Java, esse controle é feito por quatro níveis de acesso.

Os quatro níveis

  • private — visível apenas dentro da própria classe.
  • default (sem modificador) — visível na própria classe e em qualquer classe do mesmo pacote.
  • protected — visível na classe, no pacote, e também em subclasses que estejam em outro pacote.
  • public — visível em qualquer lugar do programa.

Na prática, o padrão mais cobrado em prova é: atributos privados, métodos públicos. Isso protege o estado interno do objeto e obriga quem usa a classe a passar pelos métodos que você definiu.

public class ContaBancaria {
    private double saldo;       // ninguém de fora acessa "saldo" diretamente
    private String titular;

    public void depositar(double valor) {
        if (valor > 0) {
            this.saldo += valor;
        }
    }
}
02

Getters e setters

Se os atributos são private, algo precisa expor um jeito controlado de ler e escrever esses valores de fora da classe. É para isso que existem os métodos de acesso.

  • Getter — método que retorna o valor de um atributo. Convenção: getNome(), ou isAtivo() para booleanos.
  • Setter — método que altera o valor de um atributo. Convenção: setNome(String nome).

O ponto principal de prova aqui não é a sintaxe — é o motivo: um setter permite validar um valor antes de aceitá-lo, e um getter permite mudar a forma como o dado é guardado internamente sem quebrar quem usa a classe.

public class ContaBancaria {
    private double saldo;

    public double getSaldo() {
        return this.saldo;
    }

    public void setSaldo(double saldo) {
        if (saldo < 0) {
            throw new IllegalArgumentException("Saldo não pode ser negativo");
        }
        this.saldo = saldo;
    }
}

Sem o setter validando, qualquer parte do código poderia colocar um saldo negativo direto no atributo. Com o atributo privado e um setter no meio, essa regra fica garantida em um único lugar.

03

Herança, sobrescrita e sobrecarga

Herança (extends) permite que uma classe reaproveite atributos e métodos de outra, numa relação do tipo "é um" — um Gerente é um Funcionario. Java só permite herdar diretamente de uma única superclasse.

Sobrescrita — @Override

A subclasse redefine um método herdado, mantendo a mesma assinatura (mesmo nome e mesmos parâmetros), para mudar o comportamento. É decidida em tempo de execução — é a base do polimorfismo dinâmico.

  • Nome e lista de parâmetros idênticos aos do método da superclasse.
  • O tipo de retorno deve ser o mesmo ou um subtipo dele (retorno covariante).
  • O modificador de acesso não pode ficar mais restritivo — de public não se pode ir para protected, por exemplo.
  • Não pode lançar exceções verificadas novas ou mais abrangentes que as do método original.
  • A anotação @Override não é obrigatória, mas faz o compilador avisar se a assinatura não bater — por isso é boa prática sempre usá-la.
public class Funcionario {
    public double calcularBonus() {
        return 100.0;
    }
}

public class Gerente extends Funcionario {
    @Override
    public double calcularBonus() {
        return 500.0; // mesma assinatura, comportamento novo
    }
}

Sobrecarga — overload

Dois métodos com o mesmo nome mas parâmetros diferentes (em quantidade, tipo ou ordem), dentro da mesma classe. É resolvida em tempo de compilação, olhando os argumentos passados na chamada.

public class Calculadora {
    public int somar(int a, int b) {
        return a + b;
    }

    public double somar(double a, double b) {
        return a + b; // parâmetros diferentes = sobrecarga válida
    }
}

Mudar apenas o tipo de retorno, mantendo os mesmos parâmetros, não caracteriza sobrecarga — o compilador não consegue diferenciar as chamadas e o código não compila.

04

Associação, agregação e composição

As três descrevem como uma classe se relaciona com outra, mas variam na força do vínculo e em quem controla o ciclo de vida de quem.

vínculo fraco

Associação

Relação genérica entre objetos que se "conhecem" e colaboram, mas têm ciclos de vida totalmente independentes. Não é necessariamente todo-parte.

ex.: Motorista e Carro

vínculo médio

Agregação

Relação todo-parte, mas a parte existe de forma independente do todo — normalmente é criada fora e apenas "recebida" pelo todo.

ex.: Time e Jogador · losango vazado

vínculo forte

Composição

Relação todo-parte em que a parte não existe sem o todo: é criada por ele e morre junto com ele.

ex.: Casa e Cômodo · losango preenchido

Em código

Associação — o Motorista recebe um Carro já pronto, apenas o usa por um instante:

public class Motorista {
    public void dirigir(Carro carro) {
        carro.acelerar();
    }
}

Agregação — o Time recebe a lista de Jogadores já existentes, geralmente pelo construtor; se o time acabar, os jogadores continuam existindo:

public class Time {
    private List<Jogador> jogadores;

    public Time(List<Jogador> jogadores) {
        this.jogadores = jogadores; // recebido pronto de fora
    }
}

Composição — a Casa cria os Cômodos dentro de si; se a Casa deixar de existir, os Cômodos vão junto:

public class Casa {
    private List<Comodo> comodos = new ArrayList<>();

    public Casa() {
        comodos.add(new Comodo("Sala")); // criado internamente
        comodos.add(new Comodo("Cozinha"));
    }
}

05

Quadro-resumo para revisão rápida

Uma última passada nos pontos que mais caem em prova, antes dos exercícios.

Modificadores

private → só a classe · default → classe + pacote · protected → classe + pacote + subclasses · public → todo mundo.

Override × Overload

Override: mesma assinatura, entre superclasse e subclasse, resolvido em tempo de execução, retorno pode ser covariante, acesso não pode ficar mais restrito. Overload: mesmo nome, parâmetros diferentes, dentro da mesma classe, resolvido em tempo de compilação.

Associação × Agregação × Composição

Força crescente do vínculo: associação (uso pontual) → agregação (todo-parte, parte independente) → composição (todo-parte, parte dependente). O losango no diagrama UML sempre fica do lado do "todo": vazado é agregação, preenchido é composição.

B. Classifique a relação

Para cada trecho, identifique se é associação, agregação ou composição.

exercício 1fácil
public class Pedido {
    private List<ItemPedido> itens = new ArrayList<>();

    public void adicionarItem(String produto, int qtd) {
        itens.add(new ItemPedido(produto, qtd));
    }
}
Ver resposta
Composição. O Pedido cria os próprios ItemPedido internamente — se o pedido for descartado, os itens não existem em nenhum outro lugar.
exercício 2fácil
public class Biblioteca {
    private List<Livro> acervo;

    public Biblioteca(List<Livro> acervo) {
        this.acervo = acervo;
    }
}
Ver resposta
Agregação. Os livros já existem antes de chegar à biblioteca e continuam existindo caso ela feche — a lista chega pronta de fora, pelo construtor.
exercício 3fácil
public class Cliente {
    public void fazerPedido(Loja loja) {
        loja.registrarPedido(this);
    }
}
Ver resposta
Associação. Cliente e Loja apenas colaboram por um instante através do parâmetro do método; nenhum dos dois é "parte" do outro e ambos existem de forma totalmente independente.
exercício 4médio
public class Escola {
    private List<Sala> salas = new ArrayList<>();

    public Escola(int numeroDeSalas) {
        for (int i = 0; i < numeroDeSalas; i++) {
            salas.add(new Sala());
        }
    }
}
Ver resposta
Composição. As salas nascem dentro do construtor da escola e não fazem sentido fora dela — se a escola for desativada, as salas somem junto.
exercício 5médio
public class Orquestra {
    private List<Musico> musicos;

    public void convocar(List<Musico> musicos) {
        this.musicos = musicos;
    }
}
Ver resposta
Agregação. Os músicos existem como profissionais independentemente da orquestra e são apenas "emprestados" a ela — continuam existindo se a orquestra for desfeita.
exercício 6difícil
public class CorpoHumano {
    private Coracao coracao = new Coracao();

    public void bater() {
        coracao.pulsar();
    }
}
Ver resposta
Composição. O coração é criado junto com o corpo e não existe (nesse modelo) fora dele — um caso clássico de vínculo forte, usado com frequência em prova como exemplo canônico de composição.

C. Override, overload ou erro?

Diga se cada par de métodos representa sobrescrita válida, sobrecarga válida, ou erro de compilação.

exercício 7fácil
// em Funcionario
public void registrarPonto() { ... }

// em Estagiario extends Funcionario
public void registrarPonto() { ... }
Ver resposta
Sobrescrita válida. Mesma assinatura entre superclasse e subclasse, mesmo nível de acesso.
exercício 8fácil
// na mesma classe Calculadora
public int somar(int a, int b) { ... }
public int somar(int a, int b, int c) { ... }
Ver resposta
Sobrecarga válida. Mesmo nome, quantidade diferente de parâmetros, na mesma classe.
exercício 9médio
// em Funcionario
public void falar() { ... }

// em Gerente extends Funcionario
private void falar() { ... }
Ver resposta
Erro de compilação. A subclasse está tentando reduzir a visibilidade do método (de public para private), o que não é permitido em sobrescrita.
exercício 10médio
// na mesma classe Relatorio
public void imprimir(String texto) { ... }
public void imprimir(String texto) { ... }
Ver resposta
Erro de compilação. Assinaturas idênticas dentro da mesma classe — não é sobrecarga, é um método duplicado, e isso o compilador rejeita.
exercício 11difícil
// em Animal
public List<Animal> reproduzir() { ... }

// em Cachorro extends Animal
public List<Cachorro> reproduzir() { ... }
Ver resposta
Sobrescrita válida. List<Cachorro> é um retorno covariante em relação a List<Animal> quando Cachorro extends Animal — Java aceita esse tipo de estreitamento no retorno.
exercício 12difícil
// em Repositorio
protected void salvar() throws IOException { ... }

// em RepositorioArquivo extends Repositorio
public void salvar() throws Exception { ... }
Ver resposta
Erro de compilação. Ampliar o acesso (protected → public) é permitido, mas lançar Exception — mais abrangente que a IOException original — não é.

D. Qual modificador usar?

Para cada cenário, escolha o modificador de acesso mais adequado.

exercício 13fácil

Um atributo que só pode ser lido e alterado dentro da própria classe, nunca de fora nem por subclasses.

Ver resposta
private — é o único nível que fecha o acesso mesmo para subclasses.
exercício 14médio

Um método que deve poder ser reaproveitado por subclasses em outros pacotes, mas não deve fazer parte da API pública da classe.

Ver resposta
protected — libera para subclasses (mesmo em outros pacotes) sem abrir para qualquer classe do programa.
exercício 15médio

Uma classe utilitária usada só por outras classes do mesmo pacote, sem virar parte da API pública do sistema.

Ver resposta
default (sem modificador) — mantém o acesso restrito ao pacote, sem expor nada além dele.
exercício 16fácil

Um método que faz parte da API que outras equipes vão consumir livremente, de qualquer pacote.

Ver resposta
public — é o único nível visível de qualquer lugar do programa.
